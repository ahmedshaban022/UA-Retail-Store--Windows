# StoreFlow Desktop — full code review

**Reviewed:** 2026-11-10, at commit `daaeb85` ("release: v1.0.2, the shop that could not be migrated")
**Scope:** the whole solution — 43,294 lines of source across 315 files, 13,429 lines of test across
79 files, plus the release pipeline, the installer and the documentation.
**Method:** build and full-suite execution, static review of every layer, and targeted runtime
probes against the built binaries for the findings that needed proving rather than reading.

---

## 1. The verdict

**The programme is feature-complete and it is well built.** It builds with zero warnings, the whole
suite is green, the app starts, migrates, seeds and runs, and the money arithmetic is correct.
What is not finished is not the feature list — it is the **wiring between the features**, and one
release that was written but never published.

Five defects would hurt a real shop, and one of them is silently wrong in a way the owner cannot
see. One release — the one that fixes the fault the last three commits were about — exists in the
repository but **does not exist for any shop**.

| | |
|---|---|
| Build | ✅ clean — 0 warnings, 0 errors (analyzers on, warnings-as-errors on) |
| Test suite | ✅ 544 / 544 green, twice in a row, no flakes |

## 3. The blockers

### C-1 · CRITICAL — An approved stock adjustment never reaches the ledger

**Files**
- `src/StoreFlow.Infrastructure/Approvals/ApprovalCommandHandlers.cs:176-243` — the path the UI uses
- `src/StoreFlow.Infrastructure/Inventory/StockCommandHandlers.cs:333-467` — the only code that posts the movement
- `src/StoreFlow.Desktop/ViewModels/ApprovalsViewModel.cs:213` — the only UI caller

**What is wrong.** A large stock adjustment does not post; it raises an approval request
(`StockCommandHandlers.cs:226-272`, `Kind = ApprovalKind.StockAdjustment`, with the delta in
`PayloadJson`) and returns `Posted = false`. The manager then opens **Approvals** and presses
**Approve**, which calls `DecideApprovalRequestCommand` →
`DecideApprovalRequestCommandHandler`. That handler reads the request, checks it is pending, checks
the approver is not the requester, sets `request.Status = Approved`, writes an
`approval.approved` audit entry, and saves.

**It never looks at `request.Kind`.** It never reads the payload, and it never touches the
inventory ledger. The handler that *does* — `ApproveStockAdjustmentCommandHandler`, which
deserialises the payload and posts the movement inside a transaction — is registered in DI
(`ServiceRegistration.cs:139`) and **has no caller anywhere in the product**. A repo-wide grep for
`ApproveStockAdjustment` returns only the handler, the DI line, the command record, and the
WritePoint enum.

**Failure scenario.** The shelf holds 20. The clerk records an adjustment of −150 units (approval is
required at |qty| ≥ 100 or |value| ≥ £1,000). The dialog correctly says "requires approval" and
posts nothing. The manager approves it. The stock is **still 20**, **no `StockMovements` row is
ever written**, and the audit trail says `approval.approved`. The request is no longer `Pending`, so
it can never be posted later either. The shop now believes it has 20 units of a product that has
none, and the till will happily sell them.

**Two smaller defects live in the same flow.**
- `DecideApprovalRequestCommandHandler:182` authorises with `Permission.SalesDiscountOverLimit` — a
  **discount** permission — for *any* approval, including a stock adjustment. The handler that does
  it correctly requires `Permission.StockApprove`.
- It forbids self-approval unconditionally (`:210`); `ApproveStockAdjustmentCommandHandler:390`
  lets an administrator approve their own. The two paths disagree.

**Fix.** Branch on `request.Kind` in `DecideApprovalRequestCommandHandler`: for
`ApprovalKind.StockAdjustment`, apply the adjustment through `InventoryLedger` inside the same
transaction as the status change, with `Permission.StockApprove`. Delete or re-route
`ApproveStockAdjustmentCommandHandler` so exactly one path can both approve and post.

### H-1 · HIGH — Changing a product's selling unit silently rescales its stock

**Files**
- `src/StoreFlow.Infrastructure/Catalog/ProductCommandHandlers.cs:166` — `product.UnitId = command.UnitId;`
- `src/StoreFlow.Infrastructure/Inventory/InventoryQueryHandlers.cs:251` — the reader
- `src/StoreFlow.Infrastructure/Inventory/InventoryLedger.cs:98-115` — the writer

**What is wrong.** `StockBalances.QuantityOnHandScaled` is a bare scaled integer whose meaning
depends on the product's *current* unit precision. Every reader divides it by `10^currentPrecision`
(`InventoryQueryHandlers.cs:251`), and `InventoryLedger.ApplyAsync` computes deltas with the current
scale too. The stored integer is never rescaled when the unit changes, and nothing is written to
`StockBalances` at that moment, so the `trg_StockBalances_NoNegative` trigger never sees it.

**Failure scenario.** "Apples" is sold by weight: 10 kg received → `QuantityOnHandScaled = 10000`
at scale 3. The owner edits the product and changes the unit to "Piece" (scale 0) — one field, no
guard (`ProductEditorViewModel.cs:437` passes `UnitId` straight through). The inventory screen now
shows **10 000 pieces** on hand, and the till will sell all 10 000 although the shelf holds 10 kg.
In the other direction: 10 pieces (scaled 10) changed to "Kilogram" (scale 3) → a 1 kg sale is
delta −1000, `ApplyAsync` computes 10 − 1000 and refuses — the product becomes **completely
unsellable** with "There is not enough stock for this sale", despite a full shelf.

**Fix.** Refuse to change a product's unit once it carries stock movements or a non-zero balance,
or convert the balance and every historical movement's scale explicitly with an audit entry. At
minimum, `SaveProductCommandHandler` must compare old and new unit precision and reject the change
when the product has a history.

### H-2 · HIGH — The recovery wizard crashes on exactly the input it exists for

**Files**
- `src/StoreFlow.Infrastructure/Backup/RecoverStoreCommandHandler.cs:69`
- `src/StoreFlow.Infrastructure/Backup/SqliteSnapshot.cs:43-57`
- `src/StoreFlow.Desktop/ViewModels/RecoveryWizardViewModel.cs:124-156`
- `src/StoreFlow.Desktop/App.xaml.cs` — `OnDispatcherUnhandledException`

**What is wrong.** `IsShopUnreadable()` calls `SqliteSnapshot.IsHealthy(paths.DatabasePath, out _)`,
which opens the file read-only and runs `PRAGMA integrity_check`. On a file that is not a SQLite
database, SQLite raises `SQLITE_NOTADB` and `Microsoft.Data.Sqlite` throws. **Proved at runtime:**

```
IsHealthy(text file)   : THREW SqliteException: SQLite Error 26: 'file is not a database'.
IsHealthy(random bytes): THREW SqliteException: SQLite Error 26: 'file is not a database'.
```

Nothing catches it. `IsShopUnreadable` does not, `RecoverStoreCommandHandler.HandleAsync` does not,
and `RecoveryWizardViewModel.RestoreAsync` has a `try { … } finally { … }` with **no `catch`**. The
exception reaches the dispatcher, where `App.OnDispatcherUnhandledException` only writes to
diagnostics and **never sets `e.Handled = true`** — so the process terminates.

**Failure scenario.** The database file is damaged into a non-SQLite file (bad sector, wrong file
replaced, truncated header). The app catches it at start-up and opens the recovery wizard — exactly
as designed. The owner picks a good `.sfb` and presses **Restore**. `IsShopUnreadable()` throws, the
app dies mid-restore, and the owner is left with no programme and no recovery. The one screen
built for the worst day in the shop's life is the thing that kills the app on that day.

**Fix.** Treat any `SqliteException` or `IOException` from the health check as "unreadable" — that
is the only sensible reading. Consider `e.Handled = true` for non-fatal UI exceptions generally
(see M-4).

### H-3 · HIGH — Stock-count variance is frozen at save time but applied at post time

**Files**
- `src/StoreFlow.Infrastructure/Inventory/StockCountCommandHandlers.cs:139-164` (variance computed)
- `src/StoreFlow.Infrastructure/Inventory/StockCountCommandHandlers.cs:449-462` (variance applied)

**What is wrong.** `SaveStockCountCommandHandler` reads the balance at save time and stores
`difference = counted − expected` on the line. `PostStockCountCommandHandler` then applies
`line.DifferenceScaled` verbatim. The balance is never re-read, so the count does not bring the
book quantity to the counted quantity.

**Failure scenario.** Balance 10, counter counts 12 → difference +2 stored. Three units sell before
the count is approved and posted (the counter cannot approve their own count, so the window is
minutes to hours). Posting applies +2 to a balance of 7 → **9, while the shelf holds 12**. The
count silently asserts a wrong number and no report shows the discrepancy. Second scenario: balance
10, counted 5 → difference −5; six units sell; posting applies −5 to a balance of 4 → the ledger
refuses ("There is not enough stock for this movement") → the whole count rolls back with a
misleading message. The count is already `Approved`, so it cannot be edited — only cancelled and
redone.

**Fix.** At post time, re-read the balance inside the posting transaction and derive the adjustment
as `counted − currentBalance` (the line already stores `CountedQuantityScaled`), instead of
replaying the difference captured at save time. If the count is meant to be a snapshot of a moment,
the posting should refuse when the balance has moved since the count was taken.

### H-4 · HIGH — A stock adjustment of 2.6 on a product sold by the piece silently becomes 3

**Files**
- `src/StoreFlow.Application/Inventory/InventoryValidation.cs:142-164` — `ValidateAdjustment`
- `src/StoreFlow.Infrastructure/Inventory/StockCommandHandlers.cs:222`
- `src/StoreFlow.Desktop/ViewModels/StockAdjustmentViewModel.cs:143-147`

**What is wrong.** Every other quantity entry path in the product checks that the quantity fits the
product's unit: the till (`PosCartBuilder.cs:97`), purchase lines (`InventoryValidation.cs:71`),
stock counts (`:189`), opening stock (`:252`) and returns (`PostReturnCommandHandler.cs:117`) all
refuse a quantity the unit cannot express. **The stock adjustment is the one path that does not.**
`ValidateAdjustment(quantityDelta, unitCost, reason)` has no unit-precision parameter and no
`FitsScale` check; the dialog only checks that the quantity parses and is not zero; and
`new UnitQuantity(2.6m, 0).ToScaledLong()` rounds **away from zero to 3**.

**Failure scenario.** The clerk types **2.6** to add stock found in the back store for a product
sold by the piece. The program accepts it, adds **3**, and reports success. The shelf holds 2.6 more
than the books say — and the books are wrong. With a negative adjustment, −2.6 removes **3**.

**Fix.** Give `ValidateAdjustment` the unit precision and apply `FitsScale`, exactly as
`ValidatePurchaseLine` already does. The scale is already available in the dialog
(`InventoryOptionItem.QuantityScale`).

### H-5 · HIGH — A price written with a decimal comma is read as 100× its value

**Files**
- `src/StoreFlow.Application/Catalog/ProductCsvMapper.cs:565-597` — `TryParseMoney`
- `src/StoreFlow.Desktop/ViewModels/ProductEditorViewModel.cs:719-724` — `TryReadDecimal`
- `src/StoreFlow.Desktop/ViewModels/InventoryInput.cs:24-41` — the **correct** implementation, used by the inventory screens

**What is wrong.** Both paths call
`decimal.TryParse(text, NumberStyles.Number, CultureInfo.InvariantCulture, out value)`. With the
invariant culture, `,` is the **thousands** separator and `.` is the decimal point. So a price
written the way most of the world writes it — `12,50` — is read as **1250**.

Proved end-to-end against the real mapper, not merely the BCL:

```
decimal.TryParse("12,50", NumberStyles.Number, InvariantCulture)  ->  1250
decimal.TryParse("450,00", ...)                                   ->  45000

ProductCsvMapper.BuildRows, sale_price cell "12.50"  -> RESOLVED salePrice = 12.50   issues=none
ProductCsvMapper.BuildRows, sale price cell "12,50"  -> RESOLVED salePrice = 1250    issues=none
ProductCsvMapper.BuildRows, sale price cell "450,00" -> RESOLVED salePrice = 45000   issues=none
```

The row is reported **valid with no issue at all**, so the import writes the inflated price
straight into the catalogue. The cost price has the same defect, which also inflates the
valuation.

**The project already solved this.** `InventoryInput.TryReadDecimal` — used by the opening-stock,
purchase, stock-adjustment and stock-count screens — handles it properly: it maps the Arabic
decimal and thousands marks (`٫` `٬`) onto their ASCII equivalents and treats a comma followed
by one or two digits as a decimal point, so `12,50` is 12.50 and `1,200` is still 1200. The
product editor and the CSV mapper each reimplemented the parse instead of calling it, and both
copies are the weaker version.

**Failure scenario.** The shop exports the catalogue, edits prices in a spreadsheet whose locale
uses a decimal comma, and re-imports. Every product is priced 100× too high, with no warning on
the row and nothing in the preview to raise it. Or the owner types `12,50` into the product
editor's sale price — the field still reads `12,50` afterwards, while the model holds 1250 — and
the till then charges 1250 for the article.

**Fix.** Route both paths through `InventoryInput.TryReadDecimal` (the CSV mapper lives in the
Application layer, so the helper should move down to `Application/Common` where both can reach
it). Reject, rather than reinterpret, any cell whose shape is ambiguous — a value like `1,234`
is a thousands separator in one locale and a price of 1.234 in another.

## 4. The release that does not exist

### M-1 · MEDIUM — v1.0.2 is committed, built and documented, but never published

This is the finding with the widest blast radius, because it is the release that fixes the fault
the last three commits were written about.

**What the repository says.** `docs/RELEASE-NOTES.md` is titled *"StoreFlow Desktop v1.0.2 — release
notes"* and reads as a published release. The commit is `release: v1.0.2, the shop that could not be
migrated`. `src/StoreFlow.Desktop/StoreFlow.Desktop.csproj` says `<Version>1.0.2</Version>`. The
installer was built: `artifacts/installer/1.0.2/StoreFlow-1.0.2-x64.msi`, 55 986 448 bytes.

**What is actually published.** Checked against the remote and the GitHub API:

```
git ls-remote --tags origin
  2940736…  refs/tags/pre-phase-2
  0cb5663…  refs/tags/v1.0.0
  371e422…  refs/tags/v1.0.1

GET /repos/ahmedshaban022/UA-Retail-Store--Windows/releases
  StoreFlow Desktop v1.0.1 | tag=v1.0.1 | draft=False | published=2026-11-04T12:59:23Z
  StoreFlow Desktop v1.0.0 | tag=v1.0.0 | draft=False | published=2026-11-04T06:59:47Z
```

**No `v1.0.2` tag. No v1.0.2 release. No row in `docs/RELEASES.md`.** The commit itself *is* on
`origin/main` (`origin/main` == `daaeb85` == local `HEAD`), and there is no `.sha256` file beside
the local MSI. `docs/RELEASES.md` calls itself "a record of what a shop actually received" and
documents the three-step procedure — step 3, "the row above is filled in from the published
release", was not done.

**Why it matters.** The v1.0.1 release notes promise the fix is "in the next release", and
`README.md` says "Both release tags already carry every migration, so a shop that has only ever run
a released version never meets the fault; the fix will be in the next release." But the next
release does not exist. A v1.0.1 shop that hits the migration fault still cannot open, and the
updater will never offer it a remedy, because the updater reads the newest *published* release.

**It is one command away.** The version and the notes are already correct in the tree, so:

```powershell
git tag v1.0.2
git push origin v1.0.2
```

The workflow will build, gate on the suite, publish the installer with its SHA-256, and create the
release. Then fill in the `docs/RELEASES.md` row from the published release, as the document says.

**A guard so it cannot happen again.** `tests/StoreFlow.Desktop.Tests/ReleaseWorkflowTests.cs`
already reads `release.yml` and asserts the workflow's internal consistency — but nothing ties the
version in the csproj to a published release. A test that fails when
`<Version>` disagrees with the newest row of `docs/RELEASES.md` would have caught this on the day it
was committed.

## 7. Why the suite stayed green

This is the most important structural observation in the review, and it is what allowed C-1 to ship
in a suite of 544 green tests.

**The tests exercise handlers; they do not exercise the wiring.** `InventoryTests.cs:379` calls
`ApproveStockAdjustmentCommandHandler` **directly**:

```csharp
Result<int> approved = await new ApproveStockAdjustmentCommandHandler(...)
    .HandleAsync(new ApproveStockAdjustmentCommand(outcome.Value.ApprovalRequestId!.Value, "Checked"), …);
approved.IsSuccess.ShouldBeTrue();
```

That test is green, and it is worthless as a guarantee: the Approvals screen never calls that
handler. `Desktop.Tests` resolves handlers the same way —
`_provider.GetRequiredService<ICommandHandler<…>>()` — so a handler that is registered but
**orphaned** resolves perfectly and looks healthy. The write-fault matrix exercises
`WritePoint.ApproveStockAdjustment` and `ApproveStockAdjustmentCommit` the same way: it proves the
handler is atomic, not that anything calls it.

**Nothing in the suite asserts that a UI screen can reach a given command.** There is no test that
walks from a ViewModel to a handler, no test that fails on a registered-but-unreachable handler, and
no test that the two approval paths cannot both exist. C-1 was invisible for exactly this reason.

Two cheap guards would have caught it:

1. A test that reflects over the `ICommandHandler<,>` registrations and fails when a handler's
   command type is not referenced by any `ViewModel` — with an allow-list for commands that are
   genuinely reached only from other handlers.
2. A test that drives the **Approvals screen** the way `PosScreenTests` drives the till: raise an
   adjustment, approve it through the screen's command, assert the stock moved and a movement
   exists.

The same gap explains H-1 and H-3: both are *seams*, not units. H-1 is a product-editor field with
no guard; H-3 is a save-then-post gap between two screens. Neither is visible to a test that calls
one handler at a time.

### 7.1 Where the suite itself is thinner than it looks

The suite is strong — 544 cases, **no skips, no assertion-free tests, no wall-clock assertions and
no unseeded randomness**, and every business day in the tests is a literal. But these rules are
not pinned, so a change to them would not turn the suite red:

- **`TableColumnWidthTests` can pass with nothing asserted.** `Columns()` does `yield break` when
  the repository root is not found (`:132-137`) and the test `continue`s when a view file is
  missing (`:142-145`). The two width guards then iterate an empty sequence and **pass**. A
  renamed `.xaml`, or a published/packed test run, silently voids them. (`AccessibleNameDebtTests`
  and `ReleaseWorkflowTests` do the right thing — `root.ShouldNotBeNull()`.)
- **`MoneyMath.Multiply`'s rounding is not exercised.** The test asserts `Multiply(19.99m, 3m) ==
  59.97m`, but `59.970m == 59.97m` is true for `decimal` — **deleting the `Round(...)` from
  `MoneyMath.cs:31` would still pass.** `ApplyRate` has the same gap.
- **The exclusive-tax rounding is untested on a fractional amount.** The tax tests use only exact
  values (`100 @ 1450bp → 14.50`, `200 @ 1000bp → 20.00`), so the `Round` on the exclusive path
  is never pinned. The *inclusive* path is pinned properly (`181.82` / `18.18`).
- **Which line receives the discount remainder is unpinned.** The test asserts the shares are each
  `0.33` or `0.34` and sum to `1.00`; it never checks that the **dearest** line got the extra
  cent. A mutation that puts it on the cheapest line passes.
- **`UnitQuantity`'s rounding direction is unpinned.** It rounds with `AwayFromZero` at its own
  call site, but the test uses `2.567` at scale 2 — not a midpoint — so `ToEven` would give the
  same answer. Scale boundaries 4, 5 and 6 are never exercised either.
- **One shared fixture, order-fragile.** `DatabaseTests` uses `IClassFixture<DatabaseFixture>`, so
  all eight tests share one seeded database, and `A_posted_stock_movement_cannot_be_edited` grabs
  `context.StockMovements.FirstAsync()` — the first movement in the shared file, not the one it
  just inserted. It passes today only because no other test in the class inserts one.
- **A machine-specific path in a test.** `CrashRecoveryTests.cs:79` falls back to a hard-coded
  `D:\dotnet` when `DOTNET_ROOT` is unset, so the test fails for environmental reasons on a
  machine that has the SDK somewhere else.
- **A stray tracked file.** `tests/StoreFlow.Application.Tests/probe.txt` is a 3-byte BOM-only
  file referenced by no test.

## 8. Checked and refuted

Two findings were raised during the review and did not survive checking. They are recorded here so
nobody spends time on them.

**"A failed restore deletes the shop's un-checkpointed sales before the swap."**
`BackupRestoreService.ReplaceDatabase` does delete the `-wal` and `-shm` **before**
`File.Move` (`:191-194`), which looks like a data-loss window. It is not one, on Windows:

- `DeleteIfPresent` (`:278-284`) does not swallow exceptions. While any connection is open the WAL
  is locked, `File.Delete` throws `IOException`, and `RestoreAsync` catches it at `:100-103` and
  reports "The shop's data could not be replaced" — **before** the move. Proved: the delete threw
  *"The process cannot access the file … because it is being used by another process."*
- When no connection is open, SQLite has already checkpointed the WAL into the database file and
  removed it, so there is nothing left to lose.

So the restore fails loudly and keeps the data, rather than losing it silently. The ordering is
still fragile and has no rollback (M-13), and the owner is shown a raw exception message — but it is
not silent data loss.

**"The read-only health check of a WAL database fails."**
A WAL-mode database opened read-only with no `-shm` present *does* work: SQLite 3.22+ opens it
read-only. Proved against the real backup path — the snapshot opened read-only, passed
`integrity_check`, and held the row that was written before the copy.

## 9. What is genuinely good

This is not a codebase in trouble. The following were checked closely and are correct, and the
report should not be read as saying otherwise.

- **The v1.0.2 migration fix is correct and complete.** The guard-trigger drop/recreate works on
  **every** migration path, not only the one the committed test covers — including migration 1 → 2,
  which rebuilds `Products` and `ProductBarcodes`, the exact tables the barcode guards reference,
  and which no test exercises. The `NOCASE` collation lands, all 12 guards are restored, and the
  pragma split means a read-only connection is never asked to change the file. The five tests in
  `MigrationTriggerTests.cs` are genuine regression tests that would fail against the old code.
- **CSV formula injection is handled.** `CsvWriter.Escape` prefixes any cell beginning with
  `=`, `+`, `-`, `@`, tab or CR with an apostrophe, and quotes cells containing a quote, a comma or
  a newline. A product named `=cmd|'/c calc'!A0` exports as `'=cmd|'/c calc'!A0` and is inert. (The
  same guard is too broad for negative numbers — see L-2.)
- **The money arithmetic is sound.** One rounding policy (`MidpointRounding.AwayFromZero`, two
  places), applied once per line; document totals are sums of already-rounded lines so they never
  drift. A discount can never exceed its base (`ClampDiscount`). The invoice-level discount spread
  across lines sums **exactly** to the discount — verified for 2 to 5 lines — and the rounding
  remainder is assigned to the dearest line, so the result does not depend on line order.
- **Posting a sale is atomic.** Invoice, lines, payments, the idempotency row, stock movements and
  the audit entry are written in one explicit transaction, and a ledger refusal rolls the whole
  thing back.
- **Idempotency is enforced by the database**, not by convention: `RequestOutcomes.ClientOperationId`
  is a primary key and `SalesInvoices.ClientOperationId` has a unique index; a replayed checkout
  returns the first answer instead of making a second sale.
- **The application layer and the database triggers agree.** `InventoryLedger.ApplyAsync` refuses a
  negative balance before writing, so the app never reaches `trg_StockBalances_NoNegative` with a
  bad value — the trigger is the second line of defence, not the first.
- **Posted documents really are frozen**, and the one column that may move (the returned-quantity
  counter) is deliberately excluded from the trigger's comparison list.
- **A return and then a reversal undo a sale exactly once**, and an invoice can be reversed only
  once (status check plus a unique index).
- **The moving average is arithmetically sound and order-correct** — it divides by an exact decimal
  `10^scale` with no integer truncation.
- **The backup is a consistent snapshot, not a file copy** — SQLite's online backup API — and the
  copy is integrity-checked and hash-verified before it is archived. Zip-slip is guarded.
- **No TLS bypass anywhere in the updater.** The installer is checksum-verified **before** it is
  launched, and a mismatch deletes the file and refuses the update.
- **The update check does not block start-up**, and a double-click cannot post a sale twice
  (`AsyncRelayCommand` forbids concurrent execution).
- **Localisation is complete**: all 711 `StringKeys` are in both resx files; only one unused
  constant is missing. Parsed both files: 710 keys each, identical key sets, and **no value
  identical between the two locales** — so there are no silent untranslated fallbacks.
- **The test suite has no dead weight.** Zero skips, zero assertion-free test methods, zero
  `DateTime.Now` assertions, zero unseeded `Random`, and every test file that touches the disk
  uses a GUID directory under `%TEMP%` — no test writes to `%AppData%` or to the repository.
- **`StoreFlow.CrashProbe` is not a test and does not pretend to be.** It is a console
  fault-injection helper that writes one sale inside a transaction and then blocks so the parent
  can kill it mid-write; the real coverage is the two facts in `CrashRecoveryTests` that spawn it
  and check the ledger afterwards.
- **`dotnet test` on the solution runs exactly the four test assemblies** — the console
  `CrashProbe` project in the solution is not picked up as a test, so there is no stray
  "no test is available" noise.
- **The tooling is honest about its own limits.** The release notes name two open limits
  (an interrupted migration cannot self-heal; the recovery wizard has no way out) and four more
  (unencrypted archives, no price-override escalation, counts that are not blind, an unsigned
  installer) rather than claiming completeness.

## 10. Recommended order of work

1. **C-1** — one stock-adjustment approval must do both the approval and the posting. Until then,
   any adjustment above the threshold is a silent no-op, and the audit trail says it happened.
2. **H-5** — route the CSV import and the product editor's number parsing through the
   `InventoryInput` helper that already gets it right. A catalogue imported at 100× its price is
   the most expensive kind of bug, because it is invisible until a customer is charged.
3. **H-2** — catch `SqliteException` in the health check. A one-line change protects the screen the
   shop opens when everything else has already gone wrong.
4. **H-3** — re-read the balance at post time. A stock count that does not make the books match the
   shelf is worse than no count at all.
5. **H-4** — add `FitsScale` to `ValidateAdjustment`. The other four quantity paths already have it.
6. **H-1** — refuse a unit change on a product that has stock history.
7. **M-1** — tag and publish v1.0.2, then fill in the release record. The fix is already written,
   tested and committed; only the tag is missing.
8. **§7** — add the two guard tests, and the §7.1 unpinned rules. Without them the next orphaned
   handler is equally invisible.
9. **M-2** — wrap the drop/migrate/restore in a `try/finally`, and consider only dropping the
   guards when a migration is actually pending.
10. The remaining medium and low findings, in the order they appear above.
